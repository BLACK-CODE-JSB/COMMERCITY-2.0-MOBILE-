1.1 Propósito del Documento

El presente documento constituye la Especificación de Requerimientos de Software (SRS) oficial para el aplicativo móvil CommerCity Mobile v2.0, desarrollado bajo el marco de trabajo de THE BLACK CODE JSB. Su propósito es definir de manera precisa, completa, verificable y no ambigua el conjunto de requerimientos funcionales, requerimientos no funcionales, reglas de negocio, restricciones técnicas y criterios de aceptación que rigen el comportamiento del sistema.

Este documento establece el contrato técnico entre todos los actores involucrados en el desarrollo: equipo de frontend móvil, equipo de backend, diseñadores UX/UI, coordinador de casos de uso y los interesados del proyecto. Sirve como base para la elaboración de diagramas de casos de uso, diagramas de secuencia, casos de prueba y la planificación de sprints.

La versión 3.0 de este SRS incorpora la especificación completa de la transición arquitectural desde el modelo de persistencia local (prototipado) hacia el modelo real de consumo de API REST centralizada, detallando cada endpoint, contrato de datos, flujo de autenticación JWT y regla de negocio que gobierna el sistema.

ℹ️ Audiencia Objetivo Este documento está dirigido a: (1) Ingenieros de software frontend y backend, (2) Coordinadores de ingeniería y arquitectos de software, (3) Analistas y testers de calidad, (4) Directivos y stakeholders del proyecto CommerCity. La lectura técnica completa es recomendada para los roles de desarrollo; los stakeholders pueden concentrarse en las Secciones 1, 2, 7 y 10.

1.2 Alcance del Sistema

CommerCity es un marketplace móvil diseñado para dinamizar el comercio local mediante la conexión directa entre compradores y vendedores dentro de un ecosistema digital urbano. El sistema permite que comerciantes locales publiquen sus productos y gestionen sus tiendas desde un dispositivo móvil, mientras que los compradores pueden explorar, comparar y adquirir productos con soporte de múltiples métodos de pago.

El alcance funcional del sistema CommerCity Mobile v2.0 comprende los siguientes módulos operacionales:

  • Autenticación y Gestión de Cuentas: Registro, inicio de sesión con JWT, recuperación de contraseña y gestión de sesiones seguras.
  • Catálogo y Exploración: Visualización de productos por categoría, búsqueda textual, paginación y detalle de producto con stock en tiempo real.
  • Carrito de Compras Persistente: Gestión del carrito sincronizada con el servidor, con control de stock, modificación de cantidades y expiración automática.
  • Procesamiento de Pedidos y Checkout: Pasarela de pago con resumen fiscal calculado por el backend (IVA 19%, Comisión 10%), confirmación atómica de transacciones y comprobante de compra.
  • Panel de Tienda para Vendedores: Gestión de inventario, publicación de productos, actualización de estados de envío y visualización de métricas financieras.
  • Mensajería y Chat: Sistema de comunicación bidireccional entre compradores y vendedores en tiempo real.
  • Notificaciones Operacionales: Alertas sobre estados de pedidos, mensajes nuevos y actualizaciones de plataforma.
  • Sistema de Calificaciones y Reseñas: Valoración post-compra de vendedores con puntuación de 1 a 5 estrellas.
  • Consola Administrativa: Panel de métricas globales, moderación de contenido y gestión de usuarios para administradores de plataforma.

Fuera del alcance de esta versión (v2.0) se encuentran: integración con pasarelas de pago externas (PSE, PayU, Stripe), logística de terceros, facturación electrónica automática DIAN, y funciones de realidad aumentada para visualización de productos.

2. Descripción General del Sistema

2.1 Perspectiva del Producto

CommerCity Mobile opera como un cliente desacoplado de arquitectura híbrida nativa (frontend) que se comunica con un servidor backend centralizado a través de una API REST. El sistema sigue el patrón arquitectural Client-Server con separación estricta de responsabilidades:

  • Cliente Móvil (Capacitor): Responsable de la interfaz de usuario, navegación, renderizado de datos y experiencia del usuario. No realiza cálculos financieros ni validaciones de negocio críticas.
  • Backend (Node.js/Express): Responsable de toda la lógica de negocio: autenticación, autorización por roles, cálculos fiscales, validación de inventario, gestión de transacciones y persistencia de datos.
  • Base de Datos (MySQL 8.0): Capa de persistencia relacional que almacena todos los datos del negocio con integridad referencial garantizada.

2.4 Restricciones Generales

El sistema está sujeto a las siguientes restricciones de diseño e implementación:

  • Sin cálculos financieros en cliente: Ningún cálculo de IVA, comisión, subtotal o total se realizará en el código JavaScript del cliente. Todos los montos provienen exclusivamente del backend.
  • Autenticación obligatoria para transacciones (con excepción del Carrito): Toda operación transaccional y de gestión en servidor exige cabecera Authorization: Bearer <token>, con la excepción explícita del carrito de compras (/api/carrito), el cual opera sin JWT mediante el identificador comprador_id.
  • Compatibilidad de plataforma: El aplicativo debe funcionar correctamente en Android 8.0 (API 26) o superior e iOS 13 o superior.
  • Puerto de Backend fijo: El backend opera exclusivamente en el puerto 3000. En emulador Android se accede mediante la IP especial 10.0.2.2.
  • Base de datos centralizada: No se permite persistencia local de datos críticos del negocio. Los datos maestros residen exclusivamente en MySQL commercity_v2.
  • Lenguaje de la interfaz: El idioma de la aplicación es español (es-CO).
  • Conformidad tributaria: El IVA se calcula conforme a la legislación tributaria colombiana vigente (19% sobre productos gravados).

3. Requerimientos Funcionales (RF)

Los requerimientos funcionales describen qué debe hacer el sistema en términos de comportamiento observable, entradas aceptadas, salidas producidas y estados que debe mantener. Cada requerimiento recibe un identificador único, un nombre descriptivo, una descripción detallada, el criterio de aceptación medible, la prioridad y la trazabilidad con el endpoint de la API.

📋 Convención de Identificadores Los identificadores siguen el patrón RF-[número] para Requerimientos Funcionales. La prioridad sigue la convención MoSCoW: M = Must Have (Debe tener), S = Should Have (Debería tener), C = Could Have (Podría tener).

3.1 Módulo de Autenticación y Cuentas

Este módulo gestiona el ciclo de vida completo de la identidad del usuario: registro, autenticación, recuperación de credenciales y cierre de sesión. Todos los flujos dependen de la API REST del backend y la base de datos commercity_v2.

RF-01 Inicio de Sesión Real con JWT

Descripción: El sistema debe autenticar al usuario enviando sus credenciales (correo electrónico y contraseña) al endpoint POST /api/usuarios/login. El backend verifica las credenciales contra la tabla usuarios de MySQL, comparando la contraseña usando bcryptjs.compare(). Al ser correctas, retorna un token JWT firmado con algoritmo HMAC-SHA256 con expiración de 7 días, junto con el objeto de usuario que incluye el array de roles obtenido de la tabla usuario_roles.

Flujo detallado:

  1. El usuario ingresa correo y contraseña en page-login y presiona "Iniciar Sesión".
  2. La app llama a CommerCityAPI.auth.login(email, password) que ejecuta POST /api/usuarios/login con body { email, password }.
  3. El backend consulta: SELECT u.id, u.nombre_completo, u.email, u.password, GROUP_CONCAT(r.nombre) as roles_str FROM usuarios u LEFT JOIN usuario_roles ur ON u.id = ur.usuario_id LEFT JOIN roles r ON ur.rol_id = r.id WHERE u.email = ?.
  4. El backend retorna { mensaje, token, usuario: { id, nombre, email, roles: ["COMPRADOR", "VENDEDOR"] } }.
  5. La app almacena el token en localStorage bajo la clave commercity_auth_token y los datos de usuario en commercity_auth_user.
  6. La función setRole(isSeller, isAdmin) actualiza la interfaz según los roles recibidos y navega a la pantalla correspondiente (page-home o page-admin).

Criterio de Aceptación: Un usuario con credenciales válidas obtiene token JWT, sus roles se asignan correctamente y la interfaz refleja sus permisos en menos de 2 segundos. Un usuario con credenciales inválidas recibe el mensaje "Credenciales inválidas" y permanece en la pantalla de login.

Manejo de errores: HTTP 401 → Limpiar sesión local + toast de error. HTTP 400 → Toast de campo faltante. HTTP 500 → Toast de "Error del servidor, intenta más tarde".

Prioridad: M — Must Have
Endpoint: POST /api/usuarios/login
Pantalla: page-login
RF-02 Registro de Nuevo Usuario

Descripción: El sistema debe permitir el registro de nuevos usuarios mediante el formulario de page-registro. El cliente envía los datos a POST /api/usuarios/register con payload { email, password, nombre_completo }. No existe solicita_vendedor: el backend siempre asigna el rol base comprador. Si el correo electrónico ya existe, el servidor responde HTTP 400 (Bad Request). Si el usuario requiere rol de comerciante, posteriormente utiliza el endpoint PATCH /api/usuarios/me/rol con { rol: "vendedor" }.

Validaciones requeridas en formulario:

  • Nombre completo: obligatorio.
  • Correo electrónico: formato válido RFC 5322, obligatorio.
  • Contraseña: mínimo 8 caracteres, obligatorio.
  • Confirmación de contraseña: debe coincidir con el campo de contraseña.
Prioridad: M — Must Have
Endpoint: POST /api/usuarios/register
Pantalla: page-registro
RF-03 Recuperación y Restablecimiento de Contraseña

Descripción: El sistema permite al usuario solicitar el restablecimiento de su contraseña enviando su correo electrónico a POST /api/usuarios/recover con { email }. El servidor genera un token temporal con vigencia estricta de 5 minutos. El restablecimiento efectivo se ejecuta mediante POST /api/usuarios/reset-password enviando { token, nuevaPassword } dentro de la ventana de expiración.

Prioridad: S — Should Have
Endpoint: POST /api/usuarios/recover & reset-password
Expiración Token: 5 minutos
RF-04 Cierre de Sesión Seguro

Descripción: Al ejecutar el cierre de sesión, el sistema debe eliminar completamente los datos de autenticación del almacenamiento local del cliente: la clave commercity_auth_token y la clave commercity_auth_user de localStorage. La función CommerCityAPI.clearSession() gestiona esta limpieza. Posteriormente, la interfaz debe restablecer el estado de roles (isSeller = false, isAdmin = false) y navegar obligatoriamente a page-login.

Expiración automática de sesión: Cuando cualquier petición al backend retorna HTTP 401 o HTTP 403, el interceptor de la función request() en api.js ejecuta automáticamente clearSession(), muestra el toast "Sesión expirada o no autorizada. Inicia sesión nuevamente." y navega a page-login.

Prioridad: M — Must Have
Acción: localStorage.clear() + navTo('login')
Pantalla: Todas (header/menú)

Debounce: 400ms

3.3 Módulo de Carrito de Compras (Excepción sin JWT)

El carrito de compras es la excepción a la autenticación obligatoria con JWT. No exige encabezado Bearer JWT: la sesión se asocia mediante el parámetro comprador_id.

5. Requerimientos No Funcionales (RNF)

Los requerimientos no funcionales (RNF) describen cómo debe comportarse el sistema en términos de atributos de calidad. No describen funcionalidades específicas sino las propiedades y restricciones del sistema en su conjunto. Estos requerimientos son tan vinculantes como los funcionales y deben verificarse durante las pruebas de aceptación.

5.1 Seguridad

RNF-01 Cifrado de Comunicaciones

Todas las comunicaciones entre el cliente móvil y el servidor backend en ambiente de producción deben realizarse sobre HTTPS con TLS 1.3. Los certificados SSL deben ser emitidos por una Autoridad Certificadora reconocida. En desarrollo se acepta HTTP en localhost. Ningún dato sensible (credenciales, tokens, información financiera) puede transmitirse sin cifrado en producción.

Métrica: 100% de peticiones en producción sobre HTTPS/TLS 1.3
RNF-02 Protección de Contraseñas

Las contraseñas de usuario nunca deben almacenarse en texto plano en la base de datos. El backend utiliza bcryptjs con un factor de costo mínimo de 10 (2^10 iteraciones) para el hashing de contraseñas antes de almacenarlas. El cliente nunca debe almacenar contraseñas en ningún medio de persistencia local.

Librería: bcryptjs v2.4.3+ — bcrypt cost 10+
RNF-03 Gestión Segura de Tokens JWT

Los tokens JWT deben firmarse utilizando el algoritmo HMAC-SHA256 (HS256) con una clave secreta de al menos 256 bits almacenada en variable de entorno (.env, nunca en código fuente). Los tokens tienen expiración de 7 días (expiresIn: '7d'). El cliente detecta tokens expirados (HTTP 401/403) y elimina la sesión local de inmediato. Los tokens nunca deben almacenarse en cookies sin el atributo HttpOnly.

Algoritmo: HS256
Expiración: 7 días
RNF-04 Control de Acceso Basado en Roles (RBAC)

El backend debe verificar el rol del usuario en cada petición a endpoints protegidos, no solo en el login. El middleware verifyToken debe validar la firma del JWT y extraer los roles. Los endpoints del prefijo /api/admin deben rechazar con HTTP 403 cualquier petición cuyo token no contenga el rol ADMINISTRADOR. Los endpoints de /api/tienda y /api/productos (POST/PUT) requieren rol VENDEDOR.

Verificación: En cada petición (middleware)

5.2 Rendimiento y Escalabilidad

RNF-05 Tiempo de Respuesta

Los endpoints del catálogo de productos (GET /api/productos) deben retornar respuesta en menos de 350 ms bajo carga estándar (hasta 100 usuarios concurrentes). Los endpoints de autenticación deben responder en menos de 500 ms. Las operaciones de checkout (transacciones complejas) pueden tomar hasta 2 segundos. El cliente debe mostrar indicadores de carga (spinners) para cualquier operación que supere los 300 ms.

Catálogo: <350ms
Auth: <500ms
Checkout: <2000ms
RNF-06 Optimización de Imágenes

Las imágenes de productos enviadas por los vendedores deben ser comprimidas en el backend antes de su almacenamiento. Las imágenes mostradas en el catálogo deben cargarse de forma optimizada (lazy loading), utilizando miniaturas para las listas y la imagen completa solo en el modal de detalle. El tamaño máximo por imagen en carga es de 5 MB.

Max tamaño: 5 MB por imagen
Estrategia: Lazy Loading en listas

5.3 Disponibilidad y Tolerancia a Fallos

RNF-07 Pool de Conexiones a Base de Datos

El backend debe gestionar las conexiones a MySQL mediante un pool de conexiones con la librería mysql2. El pool debe configurarse con un máximo de 30 conexiones concurrentes. Las conexiones inactivas deben liberarse automáticamente. En caso de pérdida de conectividad con la base de datos, el servidor debe retornar respuestas de error apropiadas (HTTP 503) sin caída del proceso Node.js.

Pool máx: 30 conexiones
Fallback: In-memory DB para desarrollo
RNF-08 Manejo Graceful de Errores

El cliente móvil debe interceptar todos los errores de red y API, mostrando mensajes descriptivos al usuario sin exponer detalles técnicos internos. La función request() en api.js implementa el interceptor central. Los códigos de error deben manejarse según el siguiente esquema: 400 (solicitud incorrecta), 401/403 (sesión expirada → logout), 404 (recurso no encontrado), 500 (error del servidor). Ningún console.error sin manejador debe detener la aplicación.

5.4 Usabilidad y Compatibilidad

RNF-09 Compatibilidad de Plataforma

El aplicativo debe operar de manera fluida y sin errores visuales ni funcionales en:

  • Android: Versión 8.0 (API 26) o superior. Motor de renderizado: Android WebView (Chromium).
  • iOS: Versión 13.0 o superior. Motor de renderizado: WKWebView (WebKit).
  • Navegador de desarrollo: Chrome 100+ / Firefox 100+ / Safari 14+.
Android min: API 26 (v8.0)
iOS min: iOS 13.0
RNF-10 Diseño Responsivo Adaptativo

El diseño de la interfaz debe adaptarse a dos breakpoints: Mobile (viewport ≤ 860px) para uso en dispositivos móviles en modo app, y Desktop/Tablet (>860px) para uso en navegador web. En modo mobile, la navegación principal es la barra inferior (.bnav). En modo desktop, se utiliza la barra lateral (.sidebar). La transición entre breakpoints debe ser fluida sin recarga de página.

5.5 Integridad y Consistencia de Datos

RNF-11 Aislamiento de Transacciones Financieras

Las transacciones de checkout deben ejecutarse con nivel de aislamiento READ COMMITTED en MySQL para prevenir condiciones de carrera (race conditions) que podrían resultar en ventas sobre inventario agotado. El backend debe implementar bloqueo optimista o pesimista según el volumen de la operación para garantizar la consistencia del stock.

Aislamiento: READ COMMITTED
Patrón: Transacción atómica con ROLLBACK
RNF-12 Precisión Fiscal

Todos los cálculos monetarios deben realizarse en el backend con precisión de centavo (2 decimales). El IVA del 19% y la comisión del 10% no deben presentar errores de redondeo que generen discrepancias entre lo mostrado al usuario y lo registrado en la base de datos. Se deben usar operaciones aritméticas de punto flotante controladas, preferiblemente con librería de decimales de precisión.

5.6 Mantenibilidad y Extensibilidad

RNF-13 Arquitectura Modular del Backend

El código del backend debe organizarse en módulos separados por dominio funcional en el directorio /routes: auth.routes.js, products.routes.js, cart.routes.js, orders.routes.js, tienda.routes.js, chat.routes.js, notifs.routes.js, admin.routes.js. El servidor central (server.js) únicamente registra los routers. El middleware de autenticación debe centralizarse en /middleware/auth.js.

RNF-14 Cliente HTTP Centralizado

El cliente móvil debe utilizar el módulo CommerCityAPI (www/api.js) como único punto de comunicación con el backend. 6.4 Modelo de Autenticación JWT

El flujo de autenticación implementado en CommerCity sigue el patrón estándar de autenticación sin estado (stateless) con JWT:

1
Solicitud de Login: El cliente envía POST /api/usuarios/login con { email, password } en JSON.
2
Verificación en BD: El backend consulta MySQL con JOIN en usuario_roles. Si el hash bcrypt coincide, procede a generar el token.
3
Generación del Token: jwt.sign({ id, nombre, email, roles }, JWT_SECRET, { expiresIn: '7d' }). El payload incluye los roles del usuario.
4
Almacenamiento en Cliente: El token se guarda en localStorage bajo la clave commercity_auth_token. El objeto de usuario en commercity_auth_user.
5
Uso en Peticiones Protegidas: El wrapper CommerCityAPI.request() en api.js inyecta automáticamente el header Authorization: Bearer <token> en cada petición.
6
Verificación en Backend: El middleware verifyToken en /middleware/auth.js valida la firma del JWT con jwt.verify() y extrae el payload. Adjunta el usuario a req.user.
7
Expiración/Invalidación: HTTP 401/403 → El interceptor de api.js limpia la sesión local y redirige a page-login con toast informativo.

6.5 Cliente HTTP Centralizado (api.js)

El módulo CommerCityAPI implementado en www/api.js centraliza toda la comunicación HTTP de la aplicación móvil:

// Detección inteligente del host según plataforma de ejecución
const BASE_URL = (window.Capacitor?.getPlatform() === 'android')
  ? 'http://10.0.2.2:3000'   // Emulador Android → host machine
  : 'http://localhost:3000'; // Desarrollo web estándar

// Interceptor central: inyecta JWT y maneja errores 401/403
async function request(endpoint, options = {}) {
  const token = getToken();
  const headers = {
    'Content-Type': 'application/json',
    ...(token ? { 'Authorization': `Bearer ${token}` } : {}),
    ...options.headers
  };

  const res = await fetch(`${BASE_URL}${endpoint}`, { ...options, headers });

  if (res.status === 401 || res.status === 403) {
    clearSession();          // Elimina token y datos locales
    showToast('Sesión expirada. Inicia sesión nuevamente.', 'error');
    navTo('login');          // Redirige a pantalla de login
    return null;
  }
  // ...
}

7. Reglas de Negocio

Las reglas de negocio definen las políticas y restricciones que rigen el comportamiento del sistema en términos comerciales y operativos. Son invariantes que deben mantenerse independientemente de la capa técnica que las implemente.

IDRegla de NegocioDescripciónImplementación
RN-01 Cálculo Exclusivo en Backend Ningún cálculo de IVA (19%), comisión (10%) o total de orden puede realizarse en el cliente móvil. Todos los montos financieros provienen del backend. Endpoint GET /api/pedidos/resumen
RN-02 IVA del 19% El Impuesto al Valor Agregado se aplica a todos los productos gravados según la normativa tributaria colombiana (Ley 1819/2016). El IVA es responsabilidad legal del vendedor, retenido y reportado por la plataforma. Cálculo en backend: iva = subtotal * 0.19
RN-03 Comisión de Plataforma 10% CommerCity retiene el 10% del valor bruto de cada transacción completada como comisión de intermediación. Este monto se descuenta del balance neto del vendedor en la liquidación. Cálculo en backend: comision = subtotal * 0.10
RN-04 Stock No Negativo El stock de un producto nunca puede ser negativo. Si una transacción intenta descontar más unidades de las disponibles, la transacción es rechazada con HTTP 400 y se hace ROLLBACK de la operación completa. Validación en backend antes de SQL UPDATE
RN-05 Carrito Expirado a 7 Días Los ítems de carrito sin actividad por más de 7 días consecutivos son eliminados automáticamente del sistema. El usuario es notificado si intenta acceder a un carrito expirado. Job programado en backend
RN-06 Asignación Automática de Rol COMPRADOR Todo usuario nuevo registrado en la plataforma recibe automáticamente el rol COMPRADOR como rol base, independientemente de si también solicita el rol VENDEDOR. Lógica en POST /api/usuarios/registro
RN-07 Cancelación Solo en Estado Pendiente Un pedido solo puede ser cancelado por el comprador cuando su estado es "Pendiente". Los pedidos "En Camino" o "Entregados" no admiten cancelación directa por el cliente. Validación en POST /api/historial/cancelar/:id
RN-08 Restitución de Stock en Cancelación Al cancelar un pedido, el stock de todos los productos incluidos debe restituirse automáticamente en la tabla productos en la misma transacción SQL de cancelación. Transacción SQL en backend
RN-09 Una Calificación por Pedido Un comprador solo puede registrar una calificación al vendedor por cada pedido completado ("Entregado"). No se permiten calificaciones múltiples para el mismo pedido. Restricción UNIQUE en BD
RN-10 Propiedad de Productos Un vendedor solo puede editar o eliminar productos que él mismo publicó. El backend verifica que el vendedor_id del producto coincida con el id del usuario autenticado en el JWT. Validación en backend: WHERE id = ? AND vendedor_id = ?
RN-11 Correo Electrónico Único El correo electrónico de cada usuario debe ser único en el sistema. No se permiten registros duplicados de email. El intento de registro con un email existente retorna HTTP 409 (Conflict). Restricción UNIQUE en columna email
RN-12 Dirección Requerida para Checkout El proceso de checkout no puede completarse si el comprador no tiene una dirección de entrega registrada en su perfil. El sistema bloquea la pasarela de pago y solicita el registro de la dirección. Validación en frontend + backend

9. Análisis de Riesgos

El siguiente análisis identifica los principales riesgos técnicos y de negocio asociados al desarrollo y operación de CommerCity Mobile v2.0, junto con las estrategias de mitigación propuestas.

IDRiesgoImpactoProbabilidadNivelMitigación
R-01 Race Condition en Stock Alto Media 🔴 Alto Transacciones SQL con nivel READ COMMITTED y bloqueo de filas durante el checkout.
R-02 Pérdida de Conectividad BD Alto Baja 🔴 Alto Pool de conexiones con reconexión automática. Fallback a in-memory DB en desarrollo. Respuestas HTTP 503 controladas.
R-03 Token JWT Comprometido Alto Baja 🟡 Medio Expiración de 7 días. HTTPS en producción. Clave secreta JWT en variables de entorno (.env), nunca en código fuente.

R-06 Discrepancia de Cálculos Fiscales Medio Media 🟡 Medio Centralización de todos los cálculos en el backend. Eliminación del código legacy de cálculo en cliente.
R-07 Carga de Imágenes Pesadas Bajo Alta 🟢 Bajo Validación de tamaño máximo (5 MB) en cliente y backend. Compresión automática en el servidor. Lazy loading en listas.
